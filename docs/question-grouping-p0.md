# 질문 관리 P0 — 판정 규칙과 평가 계획

상태: P0 평가 초안. P0 작성 시점에는 제품 기능 변경 없음. 후속 구현은 `question-management-progress.md` 참조. 규칙·라벨은 GPT 초안이며 강사/팀 독립 검수가 필요하다.

## 판정 원칙

|분류|정의|처리|
|---|---|---|
|동일 질문|대상·의도·조건이 같아 하나의 답변으로 함께 해결 가능|그룹 후보로 연결|
|관련 질문|주제는 같으나 출처/의미/예시/조건 등 답변 요구가 다름|별도 그룹, 관련 링크|
|모호한 질문|대상이나 의도를 특정할 근거 부족|확인 대기, 문맥별 혼란 신호 집계|
|위치 충돌|질문에 명시된 대상과 PIN 위치가 불일치|원문 보존, 위치 확인 후 그룹 판단|

- 페이지가 같다는 이유만으로 병합하지 않는다. 다른 페이지라도 동일 대상을 확실히 가리키면 병합 후보가 될 수 있다.
- '모르겠어요' 50건은 문맥별 혼란 신호이지 구체적인 질문 50건이 같은 뜻이라는 증거가 아니다.
- 위치는 단서 중 하나다. 오류가 있어도 질문은 버리지 않는다.
- 질문 수, 고유 질문자 수, 공감 수는 별도로 집계한다.
- 그룹 변경은 원문을 수정/삭제하지 않고 연결만 바꾼다. 병합·분리는 되돌릴 수 있어야 한다.
- 그룹 답변 완료는 모든 참여자의 이해 완료를 의미하지 않는다.

## 접수와 분석 계약 (P1 구현 대상)

먼저 질문을 영속 저장하고 접수 성공을 알린다. 분석 상태는 pending/running/ready/needs-review/failed로 별도 관리한다. 보류·답변 완료 등 수업 처리 상태와 섞지 않는다. 재시도는 같은 요청 키로 중복 생성을 막는다.

현재 자동 PIN hook은 분석 후 addQuestion을 호출하므로 분석 실패 시 영속 접수가 보장되는 구조가 아니다. 위치 미확정 질문을 기존 스키마가 지원하는지 확인한 뒤 P1에서 변경한다. 이번 P0에서는 DB/제품 코드를 변경하지 않는다.

## 평가 자료

`experiments/question-grouping/p0-evaluate.mjs`에 18개 진단 쌍을 정의했다. 전체를 합성/변형 사례로 명시한다. 기존 `experiments/semantic_regions/fixtures/model_benchmark_pin_review.json`의 Q009~Q012 대상(공감 지표, 사용 의사, 감정/음성 인식 기술)을 일부 변형에 사용했다. 실제 질문 원문을 복원했다고 주장하지 않는다. 좌표는 합성이다.

기대 분류는 현재 함수 결과를 보기 전에 작성했다. 독립된 사람이 검수한 gold set이 아니므로 수치를 서비스 정확도로 사용하지 않는다. 동일 질문 탐지와 '자동 병합해도 되는가'의 정책 차이에 주의한다. 기존 함수는 추천용이지 자동 그룹 병합기가 아니다.

실행: `node --experimental-strip-types experiments/question-grouping/p0-evaluate.mjs`

출력: 같은 디렉터리 `p0-results.json`, `p0-results.md`.

이번 baseline은 실제 기존 findRelatedQuestions 함수를 호출하되 임베딩을 전달하지 않는 lexical-only 평가다. 모델 성능/LLM 시간/100명 부하를 측정하지 않는다. 임베딩 결과를 임의 숫자로 만들어 비교하지 않는다.

## 구현 진행 범위 (2026-09-26 사용자 진행 승인)

- AI 분석 전에 원문을 접수한다. 위치가 없으면 좌표를 만들지 않고 null로 저장한다.
- 접수 요청 ID를 재사용하여 네트워크 재시도 중 중복 저장을 방지한다.
- 위치 분석 실패/취소는 접수된 질문을 삭제하지 않는다. 기존 질문에 위치를 붙인다.
- 자동 묶음은 우선 동일 문구·같은 페이지·근접 PIN만 허용하는 보수적인 기준이다.
  모호한 표현과 위치 미확정 질문은 별도로 표시하고 의미적 중복이라고 주장하지 않는다.
- 강사에게 원문 확인과 대표 질문 선택을 제공한다. AI 답변은 선택한 질문에만 생성한다.
- 부하 측정은 로컬 실측 범위와 미검증 영역을 분리한다. 운영 서버 100명 보장을 하지 않는다.
- FastAPI 배포 분리와 영속 그룹 처리/되돌리기는 별도 검증 없이 완료로 표시하지 않는다.

## 다음 평가

### 묶음 답변 전송 (2026-09-27 사용자 후속 진행 승인)

강사가 묶음 원문을 확인하고 같은 답변을 명시적으로 전송한다. 작성 시작 시 원문과
대상 ID를 고정하며 새 질문은 추가하지 않는다. 1~1000개 원문, 답변 1~2000자.
하나라도 변경/삭제/타 강사 소유/이미 처리됨이면 전체 전송을 거절한다.
기존 answers 및 상태 트리거를 재사용하고 한 DB 트랜잭션으로 저장한다.
답변별 요청 UUID를 유지하여 같은 요청 재시도는 중복 등록하지 않는다.
전송 실패 시 초안을 보존한다. 대표 질문만 답변하는 기존 기능은 유지한다.
운영 DB 적용은 범위 밖이며 기존 로컬 DB를 초기화하지 않는다.

### 2026-09-27 실시간 진행 UX (사용자 대화에서 진행 승인)

정교한 모델 비교보다 질문 선택·답변 흐름을 먼저 검증한다. 기존 묶음 패널에
‘5묶음 고정해서 답변하기’를 제공한다. 고정 시점의 원문 ID와 순서만 유지하고,
새 질문은 별도 건수로 알린다. 원문 수정·삭제·처리 상태는 최신 데이터를 따른다.
완료·보류 후 빈자리를 자동 채우지 않으며 ‘다음 5묶음 불러오기’로 갱신한다.
원문 펼치기, 보류·복귀, 완료·취소와 기존 개별 답변 경로는 유지한다.
새 DB 상태나 참여자에게 보이는 ‘답변 중’ 상태는 이번 단계에서 만들지 않는다.
평가: 유입 중 순서 유지, 신규 원문 오완료 방지, 완료/삭제 반영, 수동 갱신.

1. 팀이 사례 라벨을 검수하고 의견 불일치를 기록한다.
2. 비식별 실제 질문을 추가하고 개발용/최종 검증용을 분리한다.
3. 실제 임베딩을 켠 같은 입력을 평가한다. 동일 질문 정밀도/재현율과 모호·위치충돌 자동 병합 건수를 따로 보고한다.
4. 그룹 단위에서는 A-B, B-C가 비슷하나 A-C는 다른 연쇄 병합 사례도 검증한다.
5. 질문 유입 순서, 수정, 삭제, 그룹 완료 후 추가 질문을 검증한다.
6. P3에서 100명 접속과 동시 제출을 구분하고 접수 누락, 중복 저장, p50/p95 대기, 최고 대기시간, AI 호출량을 측정한다.

수치 합격선은 독립 검수 후 확정한다. 지금은 명시적인 다른 의도·부정·위치 불확실 사례를 무조건 자동 병합하지 않는 것을 우선 진단 기준으로 삼는다. 샘플링은 이 평가 이후 필요성을 판단한다.
